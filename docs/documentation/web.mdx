title: Flutter Web Testing
---

Patrol provides support for running integration tests on Flutter web applications using
[Playwright](https://playwright.dev/), a powerful browser automation framework. This allows you to handle native web
browser interactions in your tests.

## How it Works

When you run Patrol tests on web, the following happens:

1. **Flutter Web Server**: Patrol starts a Flutter web server that serves your application
2. **Playwright Test Runner**: Patrol automatically launches Chromium using Playwright, or connects to a [remote browser](#running-tests-on-a-remote-browser)
3. **Platform Actions Bridge**: For platform automation calls (like `$.platform.web.grantPermissions()`), your Dart test code sends requests to Playwright with actions to be executed
4. **Results Collection**: Test results are collected and reported back in Patrol's standard format

This architecture allows you to write the same Patrol tests that work across mobile and web platforms, with Playwright handling browser-specific interactions.

## Prerequisites

Before running Patrol tests on web, ensure you have installed [Node.js](https://nodejs.org/).

## Running Tests on Web

To run your Patrol tests on web, use the `--device` flag with `chrome`, e.g.:

```bash
patrol test --device chrome --target patrol_test/login_test.dart
```

<Info>
  When you first run tests on web, Patrol will automatically install Node.js
  dependencies including Playwright and its browser binaries. This may take a
  moment.
</Info>

### Running Tests in your CI pipeline

CI environments typically do not provide a graphical display. For this reason, it's recommended to run Patrol web tests in **headless mode**.

By default, Patrol runs web tests in headed mode (with a visible browser window).  
In CI pipelines (e.g. GitHub Actions, GitLab CI), it's recommended to enable headless mode using `--web-headless`:

```bash
patrol test \
  --device chrome \
  --target patrol_test/login_test.dart \
  --web-headless
```

### Running Tests on a Remote Browser

By default, Patrol launches the browser on the machine that runs `patrol test`.
To use a browser on another machine instead, such as a Playwright server in a
container or a hosted browser grid, pass the server's WebSocket URL with
`--web-connect-ws-endpoint`:

```bash
patrol test \
  --device chrome \
  --release \
  --target patrol_test/login_test.dart \
  --web-connect-ws-endpoint ws://browsers.internal:3000/
```

Patrol then connects to that server for test discovery and for every test, and
skips installing a local browser. A remote browser runs headless unless you pass
`--no-web-headless`; test discovery always runs headless.

`--web-browser-timeout` also limits how long Patrol waits to connect. Without
it, a server that never answers keeps the run waiting.

Options that point at files on your machine don't apply to a remote browser:
the server ignores `--web-executable-path`, `--web-downloads-path` and
`--web-traces-dir`. `--web-ignore-default-args true` isn't supported either;
pass a JSON list of the arguments to skip instead.

#### Starting a Playwright server

Any server that speaks Playwright's protocol works. To host one yourself, run
Playwright's `run-server` command with Node.js:

```bash
npx playwright@1.56.0 run-server --port 3000 --host 0.0.0.0
```

or use the official Docker image:

```bash
docker run -p 3000:3000 --rm --init -it --workdir /home/pwuser --user pwuser \
  mcr.microsoft.com/playwright:v1.56.0-noble \
  /bin/sh -c "npx -y playwright@1.56.0 run-server --port 3000 --host 0.0.0.0"
```

<Warning>
  The server must run the same Playwright version as Patrol's web runner (the
  `playwright` version in `web_runner/package.json` of the `patrol` package you
  use; 1.56.0 in the examples above). Only the major and minor versions are
  compared, so 1.56.x works with 1.56.0. With a different version the
  connection fails with `428 Precondition Required` and a "Playwright version
  mismatch" message.
</Warning>

#### How the remote browser reaches your app

Patrol serves your app on `localhost` of the machine that runs `patrol test`.
A remote browser can't open that address by itself, so Patrol tunnels it: by
default, requests from the remote browser to `localhost`, `127.0.0.1` and
`::1` go through the connection back to your machine (Playwright's
[`exposeNetwork`](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-option-expose-network)
set to `<loopback>`). To expose other hosts, pass your own rules with
`--web-connect-expose-network`, e.g. `<loopback>,*.internal.example.com`. If
the server reaches your app some other way, such as a provider's own tunnel,
pass an empty value to turn this off.

Every test loads the app again through this connection. Keep the server close
to the machine that runs `patrol test`.

<Warning>
  Use `--release` (or `--profile`) with a remote browser. A debug build is made
  of over a thousand files, which makes every test slow to load over the
  connection, and Flutter's debug service can stop starting the app after the
  first few tests on a remote browser. They then fail with a timeout in
  `initialise`.
</Warning>

#### Securing the server

`playwright run-server` has no authentication. Anyone who can reach its port
can start browsers on it. Keep it on a private network, behind a firewall or a
VPN, or reach it through an SSH tunnel. If you put an authenticating proxy in
front of it, send the credentials with `--web-connect-headers`:

```bash
export PATROL_WEB_CONNECT_HEADERS='{"Authorization": "Bearer <token>"}'
patrol test --device chrome --web-connect-ws-endpoint wss://browsers.example.com/
```

Every `--web-connect-*` option can also be set as an environment variable
(`PATROL_WEB_CONNECT_WS_ENDPOINT`, `PATROL_WEB_CONNECT_HEADERS`,
`PATROL_WEB_CONNECT_EXPOSE_NETWORK`). Prefer the environment variables for
anything secret, so it doesn't end up in your shell history or CI logs.

<Warning>
  Playwright prints the endpoint URL in its errors and reports, without the
  query string but with any `user:password@` part. Pass credentials in a header
  or in the query string, never as `user:password@` in the URL.
</Warning>

#### Hosted browser grids

Some providers offer browsers through a Playwright WebSocket endpoint. Pass
that endpoint to `--web-connect-ws-endpoint`, usually with credentials and
browser settings in the URL. Check that the provider supports the Playwright
version Patrol uses. Each `--web-workers` worker opens its own browser, which
counts as a parallel session with most providers. If the provider has its own
tunnel to `localhost`, you can use it instead of `exposeNetwork` by passing
`--web-connect-expose-network ""`.

### Supported Native Actions on Web

Patrol supports the following platform actions through Playwright:

```dart
// Dark mode
await $.platform.web.enableDarkMode();
await $.platform.web.disableDarkMode();
// Keyboard input
await $.platform.web.pressKey(key: 'a');
await $.platform.web.pressKeyCombo(keys: ['Control', 'a']);
// Permissions
await $.platform.web.grantPermissions(permissions: ['clipboard-read', 'clipboard-write']);
await $.platform.web.clearPermissions();
// Clipboard
await $.platform.web.setClipboard(text: 'test');
final clipboard = await $.platform.web.getClipboard();
// Browser navigation
await $.platform.web.goBack();
await $.platform.web.goForward();
// Cookies
await $.platform.web.addCookie(name: 'test_cookie', value: 'cookie_value', url: 'http://localhost:8080');
final cookies = await $.platform.web.getCookies();
await $.platform.web.clearCookies();
// File operations
final fileContent = utf8.encode('Hello from Patrol file upload test!');
final file = UploadFileData(
  name: 'example_file.txt',
  content: fileContent,
  mimeType: 'text/plain',
);
await $.platform.web.uploadFile(files: [file]);
final downloads = await $.platform.web.verifyFileDownloads();
// Dialogs - because of blocking nature of dialogs, dialogs need to be subscribed to before triggering
final dialogFuture = $.platform.web.acceptNextDialog();
// ... trigger the dialog ...
final dialogText = await dialogFuture;
final dialogFuture = $.platform.web.dismissNextDialog();
// ... trigger the dialog ...
final dialogText = await dialogFuture;
// Web element interactions (for iframes and external HTML)
await $.platform.web.scrollToWeb(selector: inputSelector, iframeSelector: iframeSelector);
await $.platform.web.enterTextWeb(selector: inputSelector, text: 'Hello from Patrol!', iframeSelector: iframeSelector);
await $.platform.web.tapWeb(selector: buttonSelector, iframeSelector: iframeSelector);
// Window operations
await $.platform.web.resizeWindow(size: Size(800, 600));
// Screenshots
await $.takeNativeScreenshot('my_tag');
```

See [Multi-page support](#multi-page-support) below for working with multiple browser pages (tabs).

## Multi-page support

Some tests need more than one browser page: a link that opens a new tab, an OAuth popup, or
an external site you want to check alongside your app. Patrol lets you open, switch between,
inspect, and close these pages from your test.

Every open page has a stable ID that Patrol returns when the page opens. The page your test
starts on is the initial page. It hosts the Flutter app under test, is always open, and can't be closed. One
page is active at a time, and platform actions (taps, text entry, navigation, and so on) run
against it. The initial page is active when the test starts.

### Opening a new page

`openNewPage` opens a page, navigates it to a URL, and returns its ID. It doesn't switch to
the new page for you, so call `switchToPage` when you want to act on it:

```dart
final pageId = await $.platform.web.openNewPage(url: 'https://example.com');
await $.platform.web.switchToPage(pageId: pageId);
```

### Switching between pages

`switchToPage` makes a page active, and `switchToInitialPage` takes you back to the Flutter app.
Actions after the switch run against the newly active page:

```dart
await $.platform.web.switchToPage(pageId: pageId);
// ... interact with that page ...
await $.platform.web.switchToInitialPage();
```

### Inspecting pages

```dart
final currentPage = await $.platform.web.getCurrentPage();    // active page ID
final url = await $.platform.web.getCurrentPageUrl();         // active page URL
final pages = await $.platform.web.getPages();                // all open page IDs
```

### Closing pages

`closePage` closes a page by ID. You can't close the initial page, and closing the active page
switches you back to the initial page:

```dart
await $.platform.web.closePage(pageId: pageId);
```

### Handling popups

When your app opens a page you didn't open yourself (for example a button that spawns a popup
window), use `waitForPopup` to catch it. Just like [dialogs](#supported-native-actions-on-web),
subscribe before triggering the action, since the popup can appear before you get to await it:

```dart
final popupFuture = $.platform.web.waitForPopup();
await $.platform.web.tap(WebSelector(cssOrXpath: '#open-popup'));
final popupId = await popupFuture;
await $.platform.web.switchToPage(pageId: popupId);
```

### Example

Opening a page, checking its URL, then cleaning up:

```dart
patrol('opens an external page in a new tab', ($) async {
  await $.pumpWidgetAndSettle(const MyApp());

  final pageId = await $.platform.web.openNewPage(url: 'https://example.com');
  await $.platform.web.switchToPage(pageId: pageId);

  final url = await $.platform.web.getCurrentPageUrl();
  expect(url, contains('example.com'));

  await $.platform.web.closePage(pageId: pageId);
  await $.platform.web.switchToInitialPage();
});
```
