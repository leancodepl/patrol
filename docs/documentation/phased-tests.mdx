title: Phased tests
---

A Patrol test is normally one Dart callback in one app process. **Phased tests**
split that callback into consecutive phases. When a phase finishes, the native
runner **kills the app and starts a new process** for the next phase.

Use this when you need to keep testing after the app's process is gone:
in-memory state is lost, `main()` runs again, and persisted files survive.

On Android Patrol stops the app with `am force-stop`, which also cancels its
alarms and scheduled jobs and removes its notifications. iOS terminates the app
without that. A phase that checks something scheduled before the kill can
therefore pass on iOS and fail on Android.

## Basic usage

Pass `phases([...])` **directly** as the `patrolTest` / `patrol` body. Wrapping
it in another callback loses the phase metadata and throws at runtime:

```dart title="patrol_test/restart_app_test.dart"
import 'dart:io';

import 'package:patrol/patrol.dart';

void main() {
  patrolTest(
    'restarts the app between phases',
    phases([
      PatrolPhase(($) async {
        await $.pumpWidgetAndSettle(const MyApp());
        // First process: write whatever you need to survive the kill.
      }),
      PatrolPhase(($) async {
        await $.pumpWidgetAndSettle(const MyApp());
        // Second process: the previous Dart isolate is gone.
      }),
    ]),
  );
}
```

The test **passes only if Dart reports success after the last phase**.

Each phase is a fresh Flutter app. Pump your root widget again at the start of
every phase (the same `createApp` / `$.pumpWidgetAndSettle` you already use).

A working example lives in
[`restart_app_test.dart`](https://github.com/leancodepl/patrol/blob/master/dev/e2e_app/patrol_test/restart_app_test.dart)
in the Patrol repository: phase 1 writes the current PID to a file, phase 2
asserts a different PID.

## setUp / tearDown and timeouts

Every phase runs in its own app process, and every process runs the code of
all the test files in the run from the top. That means:

- `setUp` / `tearDown`, `patrolSetUp` / `patrolTearDown` and `setUpAll` /
  `tearDownAll` run **in every phase's process**, not once for the whole phased
  test.
- Plain `setUp` / `tearDown` and `setUpAll` / `tearDownAll` also run for the
  other tests of the run in that process: for the ones before your test right
  before its next phase starts, and for the ones after it between a phase
  passing and the kill. `patrolSetUp` / `patrolTearDown` run only for the test
  the native side asked for.
- The test `timeout` applies to **each** phase separately.

So a hook that clears storage or logs out can delete the state the next phase
is meant to find after the kill. Put such cleanup in `patrolTearDown` and skip
it while `PatrolBinding.instance.willRelaunchApp` is `true`: it becomes `true`
once a phase that isn't the last one passes. To run something only in the
first process, check `PatrolBinding.instance.currentPhaseIndex` in
`patrolSetUp` (`0` for the first phase and for tests without phases):

```dart
patrolSetUp(() async {
  if (PatrolBinding.instance.currentPhaseIndex == 0) {
    await seedTestData(); // only before the first phase
  }
});

patrolTearDown(() async {
  if (PatrolBinding.instance.willRelaunchApp) {
    return; // the next phase checks this state after the relaunch
  }
  await clearStorage();
});
```

Plain `setUp` / `tearDown` and `setUpAll` / `tearDownAll` can't tell the
phases apart, so keep state resets out of them in a run with phased tests.

## How to launch the next process

By default the next phase starts the same way as a normal Patrol launch (the
app's launcher activity / default URL).

To open the next process through a deep link, set `launch` on **that** phase
(phase 2 or later). Prefer a **custom scheme** your app already handles
(`myapp://settings`), or a host you have registered as an Android App Link /
iOS Universal Link. A bare `https://` URL that the OS opens in Safari will not
reach your app:

```dart
patrolTest(
  'cold-starts from a deep link after a kill',
  phases([
    PatrolPhase(($) async {
      await $.pumpWidgetAndSettle(const MyApp());
      // ...
    }),
    PatrolPhase(
      ($) async {
        await $.pumpWidgetAndSettle(const MyApp());
        // Assert the route / screen the URL opened.
      },
      launch: PatrolAppLaunch.deepLink('myapp://settings'),
    ),
  ]),
);
```

`PatrolAppLaunch.normal()` is the default. A non-normal `launch` on the **first**
phase is rejected: that process is already started by the native runner before
Dart runs.

### Platform notes for deep links

- **Android:** the launch intent's data becomes the engine's initial route, so
  Flutter's built-in deep linking / `WidgetsApp` can open the matching screen.
- **iOS:** Flutter's built-in deep linking does **not** receive the URL in a
  Patrol process (the first frame belongs to `flutter_test`). Read the initial
  link with a native plugin such as [`app_links`] instead. A phase launched
  through a deep link needs iOS 16.4 or newer: below that, XCTest can't open a
  URL in the app, and the test fails before the app is killed.

## Continuing in the running app

`PatrolAppLaunch.attach()` starts a phase **without killing the app**. Use it
when the previous phase can make the app restart its Flutter engine while the
process keeps running. On Android this happens when the activity is destroyed
and created again, for example by a deep link that the app opens in a cleared
task. The Dart test runs in the engine, so it cannot continue past that point
on its own.

```dart
patrolTest(
  'opens a link while the app is running',
  phases([
    PatrolPhase(($) async {
      await $.pumpWidgetAndSettle(const MyApp());
      // ...
      await $.platform.mobile.openUrl('https://example.com/path');
    }),
    PatrolPhase(
      ($) async {
        await $.pumpWidgetAndSettle(const MyApp());
        // Assert the screen that the link opened.
      },
      launch: const PatrolAppLaunch.attach(),
    ),
  ]),
);
```

The phase before an `attach()` phase ends in one of two ways:

- **The engine restarts.** The phase ends there, even in the middle of its
  callback, and the code after that point does not run. The next phase runs in
  the new engine.
- **The engine keeps running.** The phase runs to its end and the next phase
  follows in the same engine. This is always the case on iOS.

On Android, Patrol waits up to 2 seconds for a new engine before it starts the
`attach()` phase in the old one. If the app restarts its engine later, the
`attach()` phase can start in the old engine, stop when that engine is
destroyed, and run again from its start in the new one.

Write the two phases so that they work in both cases:

- Make the action that can restart the engine the last step of its phase.
- Begin the `attach()` phase by waiting for the screen that the restart shows,
  before any action that changes the app.
- Do not pass Dart objects from one phase to the next. Use files or other
  persisted state.
- The process is the same, so native in-memory state survives.

Hooks follow the engine, not the phase:

- **After an engine restart** the new engine runs the test files from the top,
  so `setUp` and `patrolSetUp` run again before the `attach()` phase, with
  `currentPhaseIndex` set to its index. The old engine's `tearDown` and
  `patrolTearDown` don't run.
- **In the same engine** the `attach()` phase continues the test body:
  `setUp` and `patrolSetUp` don't run again, and `tearDown` runs once, after
  the last phase that runs in that engine. `currentPhaseIndex` changes to the
  index of the phase that is running.
- `willRelaunchApp` stays `false` before an `attach()` phase, since the app
  isn't killed.

If the engine restarts in a test that has no `attach()` phase at that point,
the test fails with a message that says so.

A working example lives in
[`engine_restart_test.dart`](https://github.com/leancodepl/patrol/blob/master/dev/e2e_app/patrol_test/engine_restart_test.dart).

## Requirements and limits

<Warning>
  **Android** phased tests need the self-instrumenting [`:patrolTest`] layout.
  The older in-app `androidTest` runner lives inside the app it would kill, so
  there a test with more than one phase fails before its first phase runs.
</Warning>

- **Android and iOS only.** On macOS, Windows and web a test with more than one
  phase fails before its first phase runs.
- **`patrol test` / `patrol build`, not `patrol develop`.** Hot Restart cannot
  survive killing the app. Phased tests throw in develop mode.
- **`--coverage` (VM) with more than one phase is not supported.** Each phase
  is a new process; coverage collection stops after the suite test count.
- A phased list must contain **at least one** phase. One phase is valid; it
  behaves like a normal test (no kill).
