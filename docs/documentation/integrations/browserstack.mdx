## Setup

[BrowserStack App Automate] is a popular cloud device farm. You can use it to run your tests on real devices.

<Accordions>
<Accordion title="Android setup">
  <Steps>
    <Step>
      ### Change runner

        Modify the **app-level build.gradle.kts**:

        ```groovy title="android/app/build.gradle.kts"
        android {
          // ...
          defaultConfig {
            //...
            testInstrumentationRunner = "pl.leancode.patrol.BrowserstackPatrolJUnitRunner"
          }
          // ...
        }

        // ...
        ```
    </Step>
  </Steps>
  That's it! You can now use `bs_android` to schedule a test run.
</Accordion>

## Schedule tests using scripts

We recommend using the [bs_android] and [bs_ios] scripts to schedule test runs.
They are part of LeanCode's [mobile-tools]. If you're using Homebrew, you can install it with:

```bash
brew tap leancodepl/tools
brew install mobile-tools
```

The scripts require the `BS_CREDENTIALS` environment variable
to be set so it can authenticate with BrowserStack:

```bash
export BS_CREDENTIALS="YOUR_USERNAME:YOUR_ACCESS_KEY"
```

Get your username and access on [BrowserStack's account page][bs_account].

Now reload your shell (e.g. `exec zsh`)

### Usage

The scripts forward all its options and flags to `patrol build`, so you can use it like this:

```bash
bs_android \
  --target patrol_test/example_test.dart,patrol_test/another_test.dart \
  --verbose \
  --dart-define 'KEY_EXAMPLE=VALUE_EXAMPLE'
```

Full example:

```
$ export BS_PROJECT=AwesomeApp # optional
$ export BS_ANDROID_DEVICES="[\"Google Pixel 4-10.0\"]" # optional
```

<Accordion title="Running tests manually">

You can follow BrowserStack's docs and/or follow the code of `bs_android` and `bs_ios` scripts:

1. Build the app under test and the instrumentation app ([see docs][patrol build])
1. Upload the app under test APK to BrowserStack ([see Android docs][bs_android_app_docs]) ([see iOS docs][bs_ios_app_docs])
1. Upload the instrumentation app APK to BrowserStack ([see Android docs][bs_android_test_docs]) ([see iOS docs][bs_ios_test_docs])
1. Start test execution on BrowserStack ([see Android docs][bs_execute_android_docs]) ([see iOS docs][bs_execute_ios_docs])

</Accordion>
</Accordions>

After scheduling the test execution, you can check the status of the test execution in the [App Automate dashboard][bs_app_automate_dashboard].

If you need to change the test configuration, check out full list of available devices and OS versions in the [BrowserStack Browsers & Devices][bs_devices].

## Dart code coverage (Android)

Patrol can collect Dart line coverage on BrowserStack and hand it back through BrowserStack's Espresso coverage API.

<Steps>
  <Step>
    Instrument the app under test: in **android/app/build.gradle.kts** set `enableAndroidTestCoverage = true` (AGP 8+; `testCoverageEnabled = true` on AGP 7) on the debug build type.
  </Step>
  <Step>
    Build with `--dart-define=PATROL_BS_COVERAGE=true`. Optionally narrow what's collected with `--dart-define=PATROL_BS_COVERAGE_PACKAGES=<regexp>,<regexp>`.

    By default only code the VM has already compiled is reported — that is, what the suite actually exercised. Add `--dart-define=PATROL_BS_COVERAGE_FORCE_COMPILE=true` to also force-compile untouched functions so never-executed lines count towards the denominator.

    <Warning>
      `PATROL_BS_COVERAGE_FORCE_COMPILE=true` is expensive, and how expensive depends on `PATROL_BS_COVERAGE_PACKAGES`.

      Set `PATROL_BS_COVERAGE_PACKAGES` to plain anchored prefixes (`^package:my_app/`, comma-separated) and Patrol hands them to the VM as library filters, so force-compilation only ever touches your own code. Leave it unset, or use real regexp syntax such as `^package:(a|b)/`, and the filter cannot be pushed down — the VM then force-compiles the whole program, Flutter framework and SDK included, on every collection. That is the difference between seconds and minutes per test.

      Within one app process the compile is paid once: Patrol tells the VM which libraries it has already compiled, so later collections skip straight to reporting. With `useOrchestrator:true` every test is a fresh process, so there is nothing to amortise and the first-collection cost is paid per test — for a large suite prefer `useOrchestrator:false` for force-compile runs.
    </Warning>
  </Step>
  <Step>
    Start the build with `"coverage": "true"` and **`"clearPackageData": "false"`** (see the warning below). `useOrchestrator` can be either value, and sharding works.
  </Step>
  <Step>
    Pull and merge the result once the build finishes:

    ```bash
    patrol bs pull-coverage --build-id <build_id> --output coverage
    ```

    Credentials come from `--creds USERNAME:ACCESS_KEY` or the `BROWSERSTACK_CREDS` env var. This writes `coverage/jacoco.exec` (Java) and `coverage/patrol_lcov.info` (Dart, merged across all shards).
  </Step>
</Steps>

<Warning>
  Coverage and `clearPackageData:true` are mutually exclusive on BrowserStack. `pm clear` between tests revokes the app's permission to write the shared coverage file, so only the first test's coverage survives — and the one remaining workaround (letting the orchestrator collect per-test coverage) is blocked by a long-standing Android bug ([android-test#829]). This is a platform limitation, not a Patrol one.

  Keep `clearPackageData:true` for your regular and nightly runs. Run coverage as a separate, periodic build with `clearPackageData:false`, accepting that a few tests which rely on a clean app/permission state may fail there. `patrol bs pull-coverage` refuses builds that ran with `clearPackageData:true` instead of handing back a misleading first-test-only result.
</Warning>
