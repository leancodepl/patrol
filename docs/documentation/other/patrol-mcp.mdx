## Overview

`patrol mcp` is an MCP ([Model Context Protocol](https://modelcontextprotocol.io)) server that lets
AI agents run and manage Patrol tests in Flutter projects. It wraps `patrol develop`, so a test runs
once and every later run is a hot restart on the same app.

It ships with [`patrol_cli`](https://pub.dev/packages/patrol_cli) — there is no separate package to
install, and the agent's tools always match the CLI that runs the tests.

An agent gets:

- `run` — runs a test file and waits for it to finish, hot-restarting an already loaded one.
- `devices` — lists attached Android and iOS devices to pass as `run`'s `device`.
- `status` — the session's state and its recent output.
- `screenshot` — a screenshot from the session's device.
- `native-tree` — the native UI tree from the session's device.
- `quit` — stops the session.

## Setup

The server is the `mcp` subcommand of the CLI, so how you launch it follows how you have `patrol_cli`.

### Globally activated CLI

```sh
dart pub global activate patrol_cli
```

```json
{
  "mcpServers": {
    "patrol": {
      "command": "patrol",
      "args": ["mcp"]
    }
  }
}
```

One server serves every project you open, and no repository needs a change.

### CLI as a project dev dependency

```json
{
  "mcpServers": {
    "patrol": {
      "command": "dart",
      "args": ["run", "patrol_cli:main", "mcp"]
    }
  }
}
```

A server launched this way runs the project's pinned CLI, so it runs tests only in that project and
the projects below it. Every `run` and `status` result names the CLI serving it in `cli`. A
globally activated server serving a project that pins another `patrol_cli` adds `cliPinWarning`,
which carries this block for the project's own config.

Editors differ only in where that block goes:

| Editor | Config file | Notes |
| --- | --- | --- |
| Claude Code | `.mcp.json` (project root) | Auto-discovered; you'll be prompted to approve on first use. |
| Cursor | `.cursor/mcp.json` | Enable MCP under **Settings → Features → MCP**. |
| Gemini CLI | `.gemini/settings.json` | `mcpServers` lives alongside other keys in this file. |
| Google Antigravity | Global — open via MCP store → **Manage MCP Servers → View raw config** | Per-workspace config isn't supported. |
| GitHub Copilot (CLI) | `.mcp.json` (project root), or `~/.copilot/mcp-config.json` (global) | Then run `/mcp` to confirm `patrol` is listed. |

The VS Code Copilot extension uses `.vscode/mcp.json` with a `servers` key and an explicit
`"type": "stdio"`:

```json
{
  "servers": {
    "patrol": {
      "type": "stdio",
      "command": "patrol",
      "args": ["mcp"]
    }
  }
}
```

See [VS Code's MCP docs](https://code.visualstudio.com/docs/copilot/chat/mcp-servers) for starting
the server.

## Which project a run happens in

`run` takes a `testFile` relative to the project, and every `run` and `status` result carries the
`projectRoot` it happened in. The server finds that project from the first of these that leads to a
`pubspec.yaml`:

1. `projectRoot` on the `run` call.
2. `--project-root` on the command line, or the `PROJECT_ROOT` environment variable.
3. The workspace roots your editor advertises over MCP.
4. `CLAUDE_PROJECT_DIR`.
5. The working directory the server was started in.

Within each of those, the project owning `testFile` wins over the nearest `pubspec.yaml` above it, so
an app in a subdirectory (or a package in a pub workspace) is reached from the repository root.

A session holds its project while it lives — the app, the device and the ports belong to it — so a
`run` naming another project is refused until the loaded session is quit.

A git worktree is a project of its own. `PROJECT_ROOT=.` in an editor config resolves to the tree the
server was started in, so a test that lives in another worktree is reached by passing that worktree as
`projectRoot`, or by naming `testFile` with its absolute path: the project owning the file wins over
every configured signal, and moves the server once no session is running.

## Options

| Option | What it does |
| --- | --- |
| `--project-root` | The project to work in, when the editor's signals don't point at it. |
| `--log-file` | Where the session writes its log. |
| `--show-terminal` | Opens a macOS Terminal window with the live log, once per log file for the server's lifetime. When it does not open, results carry `terminalWarning`. |
| after `--` | Flags for `patrol develop`, e.g. `patrol mcp -- --flavor dev --verbose`. |

`PROJECT_ROOT`, `SHOW_TERMINAL` and `PATROL_FLAGS` work as well, and the CLI's own environment
variables apply — `PATROL_FLUTTER_COMMAND` overrides which Flutter the develop session uses.

Under FVM, the develop session uses the pinned Flutter automatically. The globally activated CLI runs
under the Dart that activated it, which is independent of the project's pin.

## Version compatibility

The server drives your project's `patrol` through this CLI, so the two have to match. See the
[compatibility table](/documentation/compatibility-table) for the pairs.

A `run` against a `patrol` this CLI cannot drive stops with the mismatch reported as
`versionWarning`, which every `run` and `status` result carries. Pass `--no-check-compatibility` in
the develop args to run anyway.

## Coming from the `patrol_mcp` package

`patrol mcp` supersedes the separate [`patrol_mcp`](https://pub.dev/packages/patrol_mcp) package.
To migrate, drop `patrol_mcp` from your `pubspec.yaml` and point your editor's MCP config at
`patrol mcp` (or `dart run patrol_cli:main mcp`) as above. `PATROL_FLAGS` becomes the arguments after
`--`, which is what lets a value contain spaces.

## Agent skills

Patrol also ships [agent skills](/documentation/other/agent-skills) that complement this server: the
MCP gives the agent the tools, while a skill teaches it how to use them to write tests well.

## When a test fails

A failed `run` carries `error`: the failing test's name, its error and the error lines patrol
reported after the failure. `output` holds the session's recent log for everything else, including
what the build writes to stderr. `logFile` names the file holding the whole log; follow it with
`tail -F` to watch a run as it goes.

## A run that goes quiet

Every `run` and `status` result carries `quietForSeconds` -- how long the session has heard nothing
from the device -- and `lastTestEntry`, the last test it saw. Once the quiet passes three minutes the
result also carries a `stallNote` naming it, and a `run` that reaches its timeout says how long the
quiet lasted. `quit` stops such a run; the next `run` starts a fresh session.

## Analytics

`patrol mcp` reports each tool call to the same anonymous usage analytics as the CLI: the tool, how
the call ended (`passed`, `failed`, `refused`, `timed_out` for a run, `ok` or `error` for the
others), how long it took, the device platform, and whether the CLI is a global install, a
project's dev dependency or a path. No paths, test names, errors or output are sent.

It follows the CLI's consent. The server never asks itself: nothing is sent until the CLI has run
once in a terminal and shown its analytics notice, and `PATROL_ANALYTICS_ENABLED=false` turns it
off.

## Troubleshooting

- Open your editor at the project root, or pass `--project-root`. When no signal leads to a project,
  the tool call lists the ones it tried.
- Run `dart pub get` in the Flutter project.
- Confirm the MCP server is enabled in your editor's settings.
- The chosen Flutter command, and everything else the session logs, goes to the server's stderr —
  your editor's MCP log.
- After a Dart or Flutter upgrade, run `patrol --version` once. The first start of a globally
  activated CLI on a new SDK prints pub's resolution output to stdout, which some editors refuse in
  place of the server's first message.
